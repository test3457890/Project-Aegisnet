# File Vault Security Plan

This document describes the **local at-rest encryption** added to the File Vault, and — just as
importantly — its limits. The goal is an honest, useful prototype protection, never an overstated claim.

## Honesty boundary (read first)

The File Vault now encrypts uploaded file **contents** at rest using **AES-GCM-256** via the Web Crypto
API. This is a real, local protection. It is explicitly **NOT**:

- end-to-end encryption,
- zero-knowledge storage,
- government-grade or military-grade security,
- protection against an attacker who already has full access to this browser profile.

Treat it as "your files are not sitting in the browser database as readable plaintext," not as
"your files are safe from a determined attacker."

## How it works

1. On the first Vault upload (or first use), a random **AES-GCM-256** key is generated with
   `crypto.subtle.generateKey`. This key is **unique per browser profile** — never hardcoded, never
   shared between users.
2. The key is exported (`exportKey("raw")`) and stored in a dedicated IndexedDB database
   (`aegisnet-vault-keys`, store `keys`, id `vault-master-key-v1`).
3. On each upload, the file's bytes are encrypted with the key and a **fresh, unique 12-byte IV**
   generated by `crypto.getRandomValues`. AES-GCM also produces an authentication tag, so tampering with
   the stored ciphertext is detected on decryption.
4. The **ciphertext** (`ArrayBuffer`) and its **IV** are stored in IndexedDB
   (`aegisnet-prototype-files`, store `files`) with `encrypted: true` and `algorithm: "AES-GCM"`.
   Plaintext is never written to IndexedDB.
5. On download, the ciphertext + IV are read, decrypted with the same per-profile key, and the recovered
   plaintext is offered as a normal download. If decryption fails, a friendly error is shown.

Code: `src/app/storage/vaultCrypto.ts` (key + encrypt/decrypt) and
`src/app/storage/prototypeFileStore.ts` (`storeEncryptedPrototypeFile`, `getDecryptedPrototypeBlob`,
decrypt-aware `downloadPrototypeFile`). UI: `src/app/screens/FileVaultScreen.tsx`.

## What IS encrypted

- The **byte contents** of files uploaded to the File Vault, at rest in IndexedDB (AES-GCM-256, per-file IV).

## What is NOT encrypted

- **File metadata**: name, type, size, upload time, uploader, SHA-256 hash, and access label — stored in
  `localStorage` as plaintext.
- **Thumbnails / type-aware preview cards**: generated from the original file and stored unencrypted in
  metadata.
- **The encryption key itself**: stored locally (see below).
- **Message attachments** (in chats): out of scope for this change; they remain stored unencrypted. Only
  the File Vault path is encrypted in this prototype.
- **Anything in transit / network**: there is no production network path; nothing here implies transport
  security.
- **Pre-existing seeded demo files**: they have no stored binary and are shown as "Not encrypted / metadata only".

## Where keys are stored

- IndexedDB database `aegisnet-vault-keys`, object store `keys`, key id `vault-master-key-v1`.
- One random 256-bit AES-GCM key **per browser profile**.
- **Documented limitation:** the key lives locally, in the same browser profile as the encrypted files
  (i.e. "next to" the data). This means the protection holds if only the file store is copied, but does
  **not** hold against anyone who can read this profile's full local storage. A production design must
  protect the key with a hardware-backed key store and/or a user secret (see "Before production").

## How recovery would work (future)

There is **no key backup or recovery in this prototype**. If the local key is lost (clearing site data or
using "Wipe Device", which deliberately clears the key), previously encrypted files **cannot be
recovered**. A future production design could add, in increasing order of effort:

1. A user passphrase that wraps the file key (PBKDF2/Argon2 → key-wrapping key), so the key is derived,
   not just stored.
2. Hardware-backed key storage (TPM / Secure Enclave / StrongBox) holding a non-extractable wrapping key.
3. Recovery options that do not weaken security: recovery codes, trusted-device backup, or the
   "Personal Storage Mesh" sharded backup described in `SECURITY_FOUNDATION_PLAN.md`.

## Current prototype limitations

- Key is stored locally and is extractable; co-located with the data.
- No passphrase, no hardware-backed key, no key rotation, no per-file key hierarchy.
- Metadata and thumbnails are unencrypted.
- No recovery: lost key = unrecoverable encrypted files.
- Browser/profile-local only; nothing syncs across devices.
- Only the Vault is encrypted; chat attachments are not.

## What attacks are still possible

- **Full local access**: anyone who can read this browser profile's IndexedDB can read both the
  ciphertext and the key, and therefore decrypt the files. This is the biggest limitation.
- **Compromised device / malware / memory scraping**: plaintext exists in memory while a file is being
  decrypted for download; a compromised OS can capture it.
- **Metadata exposure**: file names, sizes, hashes, and thumbnails reveal information even though contents
  are encrypted.
- **Tampering with metadata**: the SHA-256 hash and access labels in localStorage can be altered locally.
- **No authentication of the user**: there is no login/device trust gating access to the key.

## What must be improved before production

1. Protect the key with a user secret and/or hardware-backed key store; make the working key
   non-extractable.
2. Encrypt (or minimize) metadata and thumbnails, not just file bytes.
3. Add a per-workspace key hierarchy so one revoked key does not expose everything
   (see `SECURITY_FOUNDATION_PLAN.md`).
4. Add safe recovery (recovery codes, trusted-device/sharded backup) and key rotation / crypto agility.
5. Add authentication and device trust before unlocking keys.
6. Independent security review before describing this as anything stronger than a local prototype.

## Verification

- Unit tests: `src/app/storage/vaultCrypto.test.ts` (AES-GCM round-trip, unique IV, tamper/altered-IV
  failure, key persistence) and `src/app/storage/prototypeFileStore.test.ts` (encrypted-at-rest storage:
  ciphertext is not plaintext, decryption recovers original size).
- E2E: the Vault smoke test uploads a file in a real browser, confirms the **Encrypted** badge, and that
  the local Download control is available.
