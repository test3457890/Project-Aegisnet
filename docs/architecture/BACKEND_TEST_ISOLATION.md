# Backend Test Isolation & Deterministic Seed Reset

## Overview
To ensure reliability and prevent state-leakage across test runs, AegisNet enforces strict test isolation and deterministic seed resets for backend validation.

## Test Database & Isolation
Backend tests (`vitest run`) are executed against an entirely **in-memory SQLite database** (`:memory:`). 
* **Which database file is used for tests?** No file is used. By injecting `DATABASE_URL=:memory:` inside `vitest.config.ts`, each Vitest test file worker instantiates its own isolated, ephemeral database connection that is destroyed automatically when the process ends.
* **How to clean test databases?** Cleaning is unnecessary. Because it runs in `:memory:`, simply restarting `vitest` provides a 100% clean schema with 0 applied migrations. No `.db` files or artifacts are left on disk.

## Deterministic Seed Reset
While unit tests use `:memory:`, the `smoke.ts` pipeline tests create a temporary physical file (e.g. `%TEMP%/aegisnet-api-smoke-XXXXXX/test.db`) to simulate the real filesystem persistence layer. 
* **How backend tests reset data?** The `src/db/reset.ts` and `src/db/seed.ts` scripts provide a deterministic seed reset for physical development databases (`dev.db`). They clear out all tables and insert static known data (like `Me`, `Other`, and known Networks) so you can return to a clean baseline at any time by running `npm run db:reset`.

## Avoiding ID Collisions Across Tests
When inserting test users or resources inside integration tests, do **not** rely on static IDs (like `user_invite_1`) or timestamp-based IDs (`Date.now()`) if tests are run concurrently. 
Instead, use the internal `makeTestId(prefix)` helper located inside the test suites:
```ts
let testCounter = 0;
const makeTestId = (prefix: string) => `${prefix}_${++testCounter}_${Math.random().toString(36).substring(2, 8)}`;
```
This guarantees uniqueness across concurrent operations and prevents unintentional SQL `UNIQUE` constraint failures or false-positive matches across tests.

## Migration Version Tests
Migration files (`migrate.ts`) are evaluated sequentially. 
* **How migration version tests should be handled?** Because the `:memory:` database starts with `0` applied migrations, the test setup automatically evaluates **all** migrations `v1` through `v4` in order on every single test run. If a migration is destructive, duplicated, or syntactically invalid, it will instantly fail the entire test suite setup block before any tests run. This serves as an inherent regression test for database schema transitions.

## Gitignore Rules
Physical development databases (e.g., `dev.db`, `dev.db-wal`, `dev.db-shm`) are strictly excluded from source control via `.gitignore`. Test databases generated by `smoke.ts` are written to the OS `%TEMP%` directory and cleaned up automatically, so they are never at risk of being committed.
